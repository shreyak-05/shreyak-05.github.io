TMI: Teaching OpenVLA
to Ignore the Fluff

2025 Shreya Kalyanaraman & Kunj Golwala ~10 min read Slides ↗

The Problem

Vision-Language-Action models like OpenVLA map vision and language directly to robot actions. They're trained on clean, structured instruction datasets — things like "pick up the alphabet soup and place it in the basket".

But real human instructions don't look like that. People say things like: "Okay, let's try the alphabet soup. Can you pick it up and put it in the basket? Try not to knock anything over while you're at it."

Same goal. Very different language. We wanted to know: how badly does this break OpenVLA, and what can we do about it?

What We Built

Language Perturbation Dataset

We created four instruction variants for each task in the LIBERO Object and Spatial suites, preserving the object, goal, and action — only changing the language form:

  • Clean — "pick up the alphabet soup and place it in the basket"
  • Paraphrased — "Take the alphabet soup and drop it in the basket"
  • Conversational — "Could you please pick up the alphabet soup and place it in the basket?"
  • Noisy — "Okay, lets try the alphabet soup. Can you pick it up and put it in the basket? Try not to knock anything over while you're at it."

Perturbations were generated with Gemini under strict constraints: the object, target, and action must be preserved. Only the linguistic surface form changes.

Two Approaches to Robustness

We compared two very different fixes:

  • External LLM Filtering — a LLaMA-3.1-8B-Instruct model preprocessing instructions before they reach OpenVLA, stripping the noise and returning a canonical command string. No retraining of OpenVLA.
  • Internal LoRA Fine-tuning — training lightweight LoRA adapters on OpenVLA itself, using a perturbed instruction dataset, so the model learns to handle noise internally.

Baseline: How Bad Is It?

The results were stark. On LIBERO Object tasks, OpenVLA with clean instructions achieves 69% success. Under noisy instructions, that drops to 17.5% — a 75% relative drop in performance. Same robot. Same task. Just different words.

Method 1: External LLM Filtering

We used LLaMA-3.1-8B-Instruct as a preprocessing step. The system prompt instructs it to act as a "robotic command simplifier" — convert any noisy instruction into a single canonical command of the form "pick up [object] and place it in [target]".

We compared one-shot vs few-shot prompting. Few-shot consistently performed better, giving the model concrete examples of the transformation we wanted.

System Prompt (One-shot)
You are a robotic command simplifier. Convert the input into a single strict command: "pick up [object] and place it in [target]". Remove all fluff, politeness, and urgency. Standardize verbs to "pick up" and "place". Output ONLY the clean command string.

Few-shot filtering recovers nearly all performance — +47.25 percentage points on noisy instructions, reaching 64.75%. For conversational and paraphrased instructions it reaches or matches the clean baseline entirely. No retraining required.

Method 2: LoRA Fine-tuning

We froze the base OpenVLA weights and trained LoRA adapters on demonstrations paired with perturbed instructions. We compared two adapter placements — linear (FFN) layers vs attention (q, k, v, o) projections — and two learning rate schedules.

Training was constrained by GPU memory (batch size ≤ 2–4, gradient accumulation up to 32 steps), limiting us to 4 epochs.

Linear-layer LoRA improved paraphrased instruction success from 56.75% → 61.25% — a real improvement, but modest. The attention-layer LoRA converged cleanly in training but produced degenerate policies at rollout time — a reminder that training loss is not rollout success.

What This Means

Filtering won. Under limited compute, modular LLM instruction filtering is more effective and more reliable than internal LoRA adaptation. It requires no retraining, adds minimal latency, and generalizes to any noise type.

That said, LoRA is the right long-term direction — a model that's inherently robust to noise is better than one that requires a preprocessing pipeline. It just needs more compute, larger effective batch sizes, and longer training horizons than we had access to.

Key Takeaway
VLAs are brittle to language surface form in ways that don't get enough attention. If you're deploying a VLA system where users give instructions naturally, you need to account for this — either with instruction preprocessing or fine-tuning on realistic data.

Future Directions

  • Combining LLM filtering + LoRA for best of both worlds
  • Longer LoRA training with larger effective batch sizes
  • Real-robot evaluation beyond LIBERO simulation
  • Studying whether noise robustness generalizes across task suites
